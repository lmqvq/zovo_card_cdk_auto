# 自定义功能开发与上线手册

本文记录 `lmqvq/zovo_card_cdk_auto` Fork 的开发、测试、Release、线上更新和回滚流程。后续添加前端页面、接入其他协议、同步上游版本或交给其他模型执行时，先阅读本文，再按清单操作。

本文不保存 SSH 密码、JWT_SECRET、GitHub Token、卡密、Session 或任何第三方 API 密钥。凭据只能通过密码管理器、Git Credential Manager、服务器环境变量或受控的 Secrets 注入。

## 一、当前线上系统

生产环境的实际链路是：

```text
用户浏览器
  ↓
Cloudflare
  ↓
Caddy（80/443，反代到本机回环端口）
  ↓ reverse_proxy 127.0.0.1:$PORT
systemd 服务 cdk-recharge
  ↓
$INSTALL/cdk-recharge
  ├── $INSTALL/web       前端静态资源
  ├── $INSTALL/data      SQLite 数据库
  ├── $INSTALL/app.env   生产配置和密钥
  └── $INSTALL/VERSION   当前版本
```

> 本文用 `$DOMAIN`、`$INSTALL`、`$PORT` 代替真实域名、安装目录和监听端口，实际值只在服务器和密码管理器里保存，不写进仓库。

服务器信息：

```text
系统：Ubuntu 22.04 LTS
架构：Linux amd64 / x86_64
服务：systemd + 独立 Linux 二进制
监听：127.0.0.1:$PORT
公网：Caddy 后置代理，Cloudflare 前置
```

生产环境沿用这条 systemd 链路。不要在服务器上执行 Docker 部署脚本，也不要通过 `git pull` 直接覆盖生产目录。

关键生产配置目前保持以下关系：

```text
DB_PATH=$INSTALL/data/<db-file>
WEB_DIR=$INSTALL/web
CDK_INSTALL_DIR=$INSTALL
UPDATE_ENABLED=1
CDK_GITHUB_REPO=<fork 仓库>
```

`DB_PATH`、`WEB_DIR`、`JWT_SECRET`、`CDK_INSTALL_DIR` 不应因为前端功能开发而修改。

## 三、开发新功能前的准备

每次开发前先执行：

```powershell
cd D:\Code\CdkCard
git switch custom
git status --short --branch
git log -1 --oneline --decorate
```

开始开发前必须确认：

- 工作区没有上一次功能遗留的未提交文件；
- 当前在 `custom` 分支；
- 没有把生产配置、数据库、Session、卡密或 Token 放进仓库；
- 新功能涉及哪些文件已经明确；
- 如果要修改数据库结构，先单独设计迁移、备份和回滚方案；
- 如果只是前端页面或文件解析，默认不增加数据库迁移。

提交时只暂存本次功能相关文件：

```powershell
git add path/to/feature-file.ts path/to/feature-view.vue
git add path/to/related-package.json path/to/package-lock.json
git diff --cached --name-status
git diff --cached --check
```

不要使用 `git add .` 代替审查。它容易把临时文件、其他任务的修改、环境文件或调试代码一起发布。

## 四、TXT/DOCX Session 上传功能的实际实现

本次功能只改了前端和前端依赖，没有改后端 API 和数据库结构。

相关文件：

- [RechargeView.vue](../frontend/src/views/user/RechargeView.vue)：选择文件、拖拽区域、错误提示和原有预检流程的衔接；
- [session-file.ts](../frontend/src/lib/session-file.ts)：浏览器本地读取 TXT、DOCX；
- [session-file.test.ts](../frontend/src/lib/__tests__/session-file.test.ts)：TXT、伪 DOCX、大小和类型校验；
- `frontend/src/i18n/locales/zh.ts`、`en.ts`：上传提示和错误信息；
- `frontend/package.json`、`frontend/package-lock.json`：加入 `fflate@0.8.2`，用于读取 DOCX ZIP 内容。

实现原则：

1. 文件先在浏览器本地读取，原始文件不会通过 multipart 上传；
2. TXT 直接读取文本；
3. DOCX 通过 `fflate` 解压 `word/document.xml`，用浏览器 `DOMParser` 提取文字；
4. 提取出的 Session 文本继续进入原有预检、兑换和绑定流程；
5. 单文件限制为 1 MiB；
6. 文件读取期间禁止点击预检，避免异步读取和提交竞态；
7. 原有手动粘贴 Session 的路径继续保留。

当前测试覆盖了 TXT 和伪 DOCX 文本。真正的 ZIP 格式 DOCX 仍应在每次上线前用真实文件手工验证一次。不要使用真实生产 Session 写进测试文件、截图或提交记录。

## 六、提交和版本号规则

确认本次 diff 只包含目标功能后：

```powershell
cd D:\Code\CdkCard
git switch custom
git add <本次功能相关文件>
git diff --cached --name-status
git diff --cached --check
git commit -m "feat: <功能说明>"
git push origin custom
```

服务器当前版本是 `1.4.34.3` 时，下一版必须更大。例如：

```text
v1.4.34.4
v1.4.35.1
v1.5.0.1
```

不要使用：

```text
v1.4.35-session
v1.4.35-custom
```

项目版本比较会去掉 `-` 和 `+` 后面的内容，因此带文字后缀容易和正式数字版本相等，导致后台判断没有更新。

创建标签：

```powershell
git tag -a v1.4.34.4 -m "feat: <功能说明>"
git push origin v1.4.34.4
```

## 七、GitHub Release 构建

当前工作流文件：[.github/workflows/release.yml](../.github/workflows/release.yml)。它会：

1. 使用标签对应的代码；
2. 使用 Go 1.24.x 构建 Linux amd64 后端；
3. 使用 Node 20 执行 `npm ci` 和 `npm run build`；
4. 生成 `cdk-bundle-linux-amd64.tgz`；
5. 生成同名 `.sha256` 校验文件；
6. 上传 `VERSION`；
7. 创建 GitHub Release。

Release 必须同时存在：

```text
cdk-bundle-linux-amd64.tgz
cdk-bundle-linux-amd64.tgz.sha256
VERSION
```

只有源码压缩包、只有前端构建产物或没有 `.sha256` 的 Release 都不能用于线上一键更新。

检查 Actions：

- Workflow 状态为 active；
- 运行状态为 success；
- Release 不是 Draft；
- Release 标签和 `VERSION` 一致；
- bundle 为 Linux amd64；
- `.sha256` 文件存在且下载成功。

如果标签推送没有生成运行记录：

1. 先检查 Fork 的 Actions 是否启用；
2. 检查标签是否已经到达 Fork；
3. 使用工作流的 `workflow_dispatch`，把 ref 指向目标标签；
4. 不要在没有构建成功前切换生产环境。

## 八、服务器更新前检查和备份

SSH 主机为用户自己的服务器。凭据不写进仓库或脚本。

连接后先只读检查（`$INSTALL` / `$PORT` 按实际值替换）：

```bash
systemctl is-active cdk-recharge
cat "$INSTALL/VERSION"
grep -E '^(DB_PATH|WEB_DIR|CDK_GITHUB_REPO|CDK_INSTALL_DIR|UPDATE_ENABLED)=' \
  "$INSTALL/app.env"
stat -c '%s' "$INSTALL/data/"*.db
curl -fsS "http://127.0.0.1:$PORT/health"
```

生产数据库已有业务数据。每次代码更新前都创建 root-only 备份：

```bash
set -e
BACKUP_DIR="/root/cdk-pre-$(date +%Y%m%d-%H%M%S)"
install -d -m 700 "$BACKUP_DIR"

systemctl stop cdk-recharge
tar -C "$INSTALL" \
  -czf "$BACKUP_DIR/install.tgz" \
  data app.env VERSION cdk-recharge web
systemctl start cdk-recharge
```

启动后要等待健康接口恢复。刚启动的进程可能需要几秒钟：

```bash
for i in $(seq 1 30); do
  if curl -fsS "http://127.0.0.1:$PORT/health"; then
    break
  fi
  sleep 1
done
systemctl is-active cdk-recharge
```

一键更新自身会备份旧二进制和 `web`，但不会备份数据库和 `app.env`。上面的独立备份仍然必须保留。

打开：`https://$DOMAIN/ops`

- 仓库是 `lmqvq/zovo_card_cdk_auto`；

- Release 不是 Draft；

更新器的实际流程见 [update.go](../backend/internal/handler/update.go)：

1. 从 Fork 的 GitHub Release 获取 bundle；
2. 下载 `.sha256` 并校验；
3. 解压并确认二进制、`web`、`VERSION` 存在；
4. 备份旧二进制和旧 `web`；
5. 原子切换前端目录；
6. 替换二进制和 `VERSION`；
7. re-exec 进程，必要时回退到 systemd restart；
8. 保留 `app.env` 和 `data` 不动。

## 十一、没有后台登录凭据时的安全备用更新流程

如果无法进入 `/ops`，可以在服务器上执行与一键更新相同的手工流程。必须先下载 bundle 和校验文件：

```bash
RELEASE_DIR=/root/cdk-release-1.4.34.4
install -d -m 700 "$RELEASE_DIR"
curl -fL -o "$RELEASE_DIR/cdk-bundle-linux-amd64.tgz" \
  https://github.com/lmqvq/zovo_card_cdk_auto/releases/download/v1.4.34.4/cdk-bundle-linux-amd64.tgz
curl -fL -o "$RELEASE_DIR/cdk-bundle-linux-amd64.tgz.sha256" \
  https://github.com/lmqvq/zovo_card_cdk_auto/releases/download/v1.4.34.4/cdk-bundle-linux-amd64.tgz.sha256

cd "$RELEASE_DIR"
sha256sum -c cdk-bundle-linux-amd64.tgz.sha256
mkdir extract
tar -xzf cdk-bundle-linux-amd64.tgz -C extract
test -x extract/cdk-recharge
test -d extract/web
test "$(cat extract/VERSION)" = "1.4.34.4"
```

替换时只处理二进制、`web` 和 `VERSION`（`$INSTALL_DIR` 为生产安装目录）：

```bash
INSTALL="$INSTALL_DIR"
BACKUP="$INSTALL/backups/manual-1.4.34.4-$(date +%Y%m%d-%H%M%S)"
install -d -m 700 "$BACKUP"
cp -a "$INSTALL/cdk-recharge" "$BACKUP/cdk-recharge"
cp -a "$INSTALL/VERSION" "$BACKUP/VERSION"

systemctl stop cdk-recharge
mv "$INSTALL/web" "$BACKUP/web"
mv "$RELEASE_DIR/extract/web" "$INSTALL/web"
cp "$RELEASE_DIR/extract/cdk-recharge" "$INSTALL/cdk-recharge.new"
chmod 755 "$INSTALL/cdk-recharge.new"
mv -f "$INSTALL/cdk-recharge.new" "$INSTALL/cdk-recharge"
cp "$RELEASE_DIR/extract/VERSION" "$INSTALL/VERSION"
chown -R root:root "$INSTALL/cdk-recharge" "$INSTALL/VERSION" "$INSTALL/web"
chmod 755 "$INSTALL/cdk-recharge"
chmod -R 700 "$INSTALL/web"
systemctl start cdk-recharge
```

启动失败时立刻恢复：

```bash
systemctl stop cdk-recharge || true
rm -rf "$INSTALL/web"
mv "$BACKUP/web" "$INSTALL/web"
cp "$BACKUP/cdk-recharge" "$INSTALL/cdk-recharge"
cp "$BACKUP/VERSION" "$INSTALL/VERSION"
chmod 755 "$INSTALL/cdk-recharge"
chmod -R 700 "$INSTALL/web"
systemctl start cdk-recharge
```

手工更新时绝对不要覆盖：

```text
$INSTALL/data
$INSTALL/app.env
```

## 十二、上线后的验收

服务级检查：

```bash
systemctl is-active cdk-recharge
systemctl is-active caddy
cat "$INSTALL/VERSION"
curl -fsS "http://127.0.0.1:$PORT/health"
curl -fsS "https://$DOMAIN/health"
curl -fsS -o /dev/null -w '%{http_code}\n' "https://$DOMAIN/"
```

应用级检查：

- `/ops` 可以登录；
- 用户首页可以打开；
- 原有手动粘贴 Session 仍能预检；
- TXT 文件选择和拖拽读取正常；
- 真实 DOCX 文件读取正常；
- 不支持的格式、空文件、超过 1 MiB 文件能显示错误；
- 卡密预览、预检、兑换进度、后台查询仍正常；
- Caddy 和 Cloudflare 没有返回 502/404；
- 如果浏览器仍显示旧资源，先强制刷新，再检查 Cloudflare 缓存。

上线时不要用真实生产卡密做重复兑换测试。文件上传可以用脱敏的固定 Session 或受控测试账号验证；Session 是敏感凭据，不能出现在日志、截图、Issue 或提交记录中。

## 十三、回滚策略

前端或后端代码出现问题时，优先回滚代码，不回滚数据库：

1. 停止 `cdk-recharge`；
2. 从本次 `backups/manual-<version>-<time>` 恢复旧二进制、`web`、`VERSION`；
3. 启动服务并检查 `/health`；
4. 保留失败 Release、日志和备份目录供分析。

只有确认数据库迁移或数据写入已经造成损坏时，才考虑恢复数据库备份。数据库回滚会丢失备份之后产生的业务数据，必须单独评估。

## 十四、前端页面优化的规则

前端页面改动通常只需要：

1. 修改 `frontend/src`；
2. 添加或更新相关测试；
3. 更新 `package.json` 和 `package-lock.json`（只有真正新增依赖时）；
4. 执行 `npm ci`、`npx vitest run`、`npm run build`；
5. 只提交本次功能文件；
6. 通过 Release bundle 发布。

前端改动不应：

- 直接修改生产 `web` 目录；
- 修改 `app.env` 中的业务密钥；
- 把依赖升级、管理员修复、主题重构混进同一个功能提交；
- 为了让类型检查通过而顺手修改无关页面；
- 删除原有粘贴输入、失败提示或回滚逻辑。

## 十五、接入其他协议或第三方 API 的规则

以 Pro20x Automate API 或其他协议为例，推荐分层：

```text
前端页面
  ↓ 只调用自己的 /api
Go 后端适配器
  ↓ 读取服务端配置和密钥
第三方协议 API
```

第三方密钥不能放在 Vue、静态 JS、`VITE_*` 公共变量、GitHub Release 或 Issue 中。密钥放在服务器 `app.env` 或已有的服务端配置存储中，并保持 `app.env` 权限为 600。

每个协议适配器至少应具备：

- 明确的请求和响应结构；
- 超时；
- HTTP 状态码和业务错误处理；
- 幂等键或重复请求保护；
- 受限重试和退避；
- 日志脱敏；
- 可关闭的功能开关；
- 不依赖真实密钥的 mock 测试；
- 失败时不重复扣款、不重复兑换的保护。

只有在确实需要持久化新数据时才增加数据库表。增加表时必须同时准备：备份、幂等迁移、旧版本兼容、失败回滚和数据验证。

## 十六、同步原始仓库新版本的流程

推荐流程：

```text
GitHub Sync fork 更新 master
        ↓
本地 fetch origin
        ↓
custom 合并 master
        ↓
解决冲突并检查自定义功能
        ↓
本地测试和生产构建
        ↓
递增数字版本 Release
        ↓
后台一键更新
```

每次上游更新后重点检查：

- `frontend/package.json` 和 `package-lock.json` 是否发生大范围变化；
- `backend` 的数据库迁移是否增加；
- `app.env` 变量名是否变化；
- `WEB_DIR`、监听端口、更新接口是否变化；
- Release 工作流是否仍然生成三个必需资产；
- 上游版本是否和自定义版本号冲突；
- Session、卡密、兑换、Webhook、后台登录是否仍兼容。

上游版本如果是 `1.4.35`，个人修订可以使用 `1.4.35.1`。不要让 Fork 的 Release 版本小于服务器当前版本。

## 十七、这次上线的事故记录和经验

### 1. 标签没有自动触发 Actions

初次推送 `v1.4.34.1` 后没有出现工作流运行记录。后来给 Release 工作流增加了 `workflow_dispatch`，以后可以用标签 ref 手动触发。以后发布后必须确认 Actions 有运行记录，不能只看 Git tag 已经存在。

### 2. `fflate` integrity 值错误

第一次构建 `v1.4.34.2` 时，GitHub Runner 的 `npm ci` 报 `EINTEGRITY`。原因是手工整理锁文件时把 `fflate` 的完整性值写错了一个字符。修复后使用 `v1.4.34.3` 成功构建。

经验：

- 新增依赖后必须使用 `npm ci` 验证锁文件；
- 不要手工猜测或复制 integrity；
- Release 失败时先读取 Actions 具体失败步骤；
- 没有成功 Release 就不能更新生产。

### 3. 服务刚启动时健康接口可能暂时拒绝连接

`systemctl start` 返回后，Go 服务还需要短暂初始化数据库和监听端口。健康检查必须带重试，不能因为第一次 `curl` 失败就立即判断服务损坏。

### 4. 一键更新需要后台登录

更新 API 受管理员认证保护。没有后台登录态时，可以使用本文的 SHA256 校验和代码备份流程执行等价的手工更新，但必须保留回滚能力。

## 十八、首页样式偏好与后续模型执行规则

本节是 LLDCard 用户端首页的固定设计规范，也是交给其他模型继续开发时的默认约束。后续模型应先阅读本节，再决定是否需要修改首页；已经确认的视觉细节不再反复向用户询问。

### 1. 这次优化中遇到的问题

- 快捷兑换按钮、操作指南激活按钮、服务图标和保障图标最初使用了不同的视觉语言：渐变矩形、黑色胶囊、浅色图标块和无容器图标混在一起。
- 服务卡片右侧箭头只是普通文字，缺少可点击控件的感觉；保障区域图标也没有独立的边框、底色和 hover 状态。
- 首页改造过程中出现过 Vue 原生非 void 标签自闭合、遗漏 `</style>` 的构建错误。`div`、`span` 等标签必须使用显式结束标签。
- Windows 开发环境可能没有 `npm` / `npx` 命令，但仓库的 `node_modules` 已存在时可以直接使用 `node node_modules/vite/bin/vite.js build` 和 `node node_modules/vitest/vitest.mjs run`。
- `.git` 目录可能受沙箱写入限制，提交前不能擅自修改 ACL 或删除未知的 `index.lock`；应先确认没有锁文件，再使用受控的 Git 写入权限。
- SSH 长脚本通过 PTY 执行时回显可能错乱。部署脚本完成后必须用新的只读连接核对版本、服务、健康接口、更新源和备份目录，不能只相信脚本回显。
- SQLite 主文件在更新前后可能因为运行期间新增 Webhook 事件而发生 SHA256 变化。判断数据安全时应结合 `PRAGMA integrity_check`、关键表行数和备份文件检查，不能要求数据库文件字节级完全相同。

- 基础方向：浅色、干净、留白充足，当前以 Slate/黑白控制台风格为基准。

## 二十、v1.4.34.8 兑换后自动解绑 ChatGPT 支付卡

本节记录 2026-11 新增的「解绑卡」功能。后续无论哪个模型接手，先读本节再改这部分代码。

发布信息：

```text
版本    v1.4.34.8
提交    85b4412
Release https://github.com/lmqvq/zovo_card_cdk_auto/releases/tag/v1.4.34.8
说明    .github/release-notes/v1.4.34.8.md
资产    cdk-bundle-linux-amd64.tgz / .sha256 / VERSION
```

### 1. 需求与边界

兑换订单 `completed` 之后，把**本次支付用的那张虚拟卡**从 ChatGPT 账号 `settings/billing → 付款方式` 里删掉。

明确的产品边界（改动时不得放宽）：

| 规则 | 原因 |
| --- | --- |
| 只处理 `product=gpt` 且 `plan` **不含 `renew`** 的订单 | `pro_20x_renew` / `pro_5x_renew` 是绑卡档，卡是给客户长期扣费用的，删了等于断客户续费 |
| 订阅 `will_renew=true` 时**不删**，排队等它变 false | 否则删了默认卡，续费会扣到账号里另一张历史卡 |
| 账号里只剩 **1 张卡**时不删 | 保留最后一张，避免账号无卡可用 |
| 尾号命中 **多张**时标 `review`，不自动删 | 防止误删用户自己的同尾号卡 |
| 目标卡是默认卡时，先把另一张设为默认再删 | Stripe 不允许直接 detach 默认支付方式 |
| 用户端页面不提示、不加步骤 | 纯后台动作，避免客服问题 |

### 2. 触发链路

```text
卡台 webhook gpt_direct.completed
  → handler.CardPlatformWebhook（webhook.go，+1 行）
  → gptcard.EnqueueFromWebhook(payload)
       ├─ 总开关未开 → 直接返回
       ├─ product != gpt / plan 含 renew / status != completed → 返回
       └─ INSERT 解绑任务（唯一键 order_id + 尾号，幂等）
            └─ go RunJob(id)（延迟「执行延迟」配置，默认 60s）

后台补偿（server.New 启动时 gptcard.Start）
  ├─ 启动即 scanOnce：扫最近 7 天 gpt_direct.completed，没入过队的补入
  └─ 每 5 分钟：scanOnce + runDue（执行到期的 pending）
```

**为什么要有补偿**：`go RunJob` 在进程重启时会丢，`webhook_events` 是持久化的，扫描补跑是唯一可靠兜底。

### 3. 判定顺序（代码：`internal/gptcard/runner.go` → `RunJob`）

```text
 0. 开关关闭 → 返回（不写状态）
 1. card_last_four 不是 4 位        → skipped(no_last4)
 2. cdk_id → 完整码 → session       → 取不到 skipped(no_session)
 3. accessToken 为空 → 用 sessionToken 刷新 → 失败 failed(token_invalid)
 4. ListCards（401/403 先刷新重试一次）
       └─ 仍 401/403 → failed(token_invalid)；其它 → backoff(network)
 5. gptcheck.Check 查 will_renew
       └─ 查询失败 → backoff(subscription_unknown)
       └─ true     → backoff(still_renewing)
 6. cards <= 1                      → skipped(last_card)
 7. 尾号匹配 0 张                   → skipped(not_found)
 8. 尾号匹配 >1 张                  → review(ambiguous)
 9. 目标是默认卡 → SetDefault(另一张) → 失败 skipped(default_card)
10. DELETE 目标卡
       ├─ 200 success=true          → done
       ├─ 401/403                   → failed(token_invalid)
       ├─ 400/409                   → skipped(default_card)
       └─ 其它                      → backoff(http_xxx)
```

`backoff` 的节奏：

- `still_renewing` / `subscription_unknown`：重查 3 次，退避 **10m → 1h → 3h**，到上限落 `skipped`；
- 网络类：最多 3 次，每次 +2 分钟，到上限落 `failed`。

### 4. 外部接口（抽象描述）

本功能只用到 ChatGPT 账单页的三个动作，都挂在 `chatgpt.com` 的支付方式接口下：

1. **列出**账号已绑定的支付方式；
2. **删除**指定支付方式（按支付方式 ID）；
3. **设为默认**（删默认卡的前置动作）。

实现时有三条硬要求（细节看 `internal/gptcard/client.go`，本文不写具体路径与字段）：

- 认证用该账号自己的 session accessToken；过期后用 sessionToken 换新 token 重试一次；
- 除认证头外还要带**账号标识头**，缺了会被后端直接拒绝；
- 必须走带浏览器 TLS 指纹的客户端（`bogdanfinn/tls-client` + Chrome profile），`net/http` 会被 Cloudflare 403。

**设为默认**的请求方法 / 路径 / body 是后台可配的，默认值已按抓包写入代码；如果上游改版，改配置项即可，不用发版。

### 5. 数据库（`internal/db/card_delete.go` + `db.go` 建表）

新增一张**解绑任务表**，字段设计原则（完整 DDL 见代码）：

| 字段类别 | 用途 |
| --- | --- |
| 业务标识 | `cdk_id`、`order_id`、`plan`、脱敏邮箱 |
| 目标卡 | 尾号、支付方式 ID、卡品牌、删前卡数 |
| 执行状态 | `action`（pending / done / skipped / review / failed）、`reason`、HTTP 状态、尝试次数、是否用过设默认 |
| Session 状态 | valid / invalid / unknown + 最后校验时间 |
| 调度 | `next_run_at`（退避重排）、创建/更新时间 |

- **只新增表，不改任何现有表结构**；
- 唯一键 `(order_id, card_last_four)` 是幂等的基础：重复 webhook、扫描补跑、手动重试都不会重复执行；
- 不在库里存 session、完整卡号、CVV。

`action` / `reason` 是管理页展示的唯一来源，改判定逻辑时同步更新前端 `cdLabel()`。

1. **不要把 `renew` 档加进来**——那类订单的卡是客户续费要用的；
2. **不要改成"删最新一张卡"**——必须按 `card_last_four` 匹配，匹配不到就不删；
3. **不要去掉 `chatgpt-account-id` 头**——抓包确认它是必需的；
4. **不要换回 `http.Client`**——会被 Cloudflare 403；
5. **不要在没有 `will_renew=false` 的情况下删**——会误伤账号里另一张卡；
6. **`session` 失效时不要重试**——`token_invalid` 直接终止，重试只会浪费请求；
7. **爆单时先调「全局请求速率」**，或直接把开关关掉第二天补跑，删卡不是交易任务；
8. 改 `action` / `reason` 枚举时，同步改 `OrderReconcile.vue` 的 `cdLabel()`，否则管理页会显示原始英文码。
